# Monetisation

## Contexte

circular.moda est une marketplace locale de vetements de seconde main pour
Buenos Aires. Le site combine :

- catalogue public ;
- fiches produits ;
- vitrines vendeurs ;
- publication vendeur ;
- mise en relation via WhatsApp ;
- newsletter catalogue ;
- cartes affiliees sponsorisees.

L'audience est encore limitee. La priorite business n'est donc pas de maximiser
le revenu immediat, mais de preparer une monetisation testable avant une
nouvelle phase d'acquisition.

## Strategie recommandee

Le modele recommande a court terme est :

1. conserver l'affiliation comme revenu passif discret ;
2. tester des boosts de visibilite pour les annonces ;
3. tester un service d'aide a la publication, potentiellement par WhatsApp ;
4. preparer les bases techniques d'un futur compte Plus/Pro ;
5. eviter pour l'instant les commissions sur vente.

Le message business central :

> Vendre plus vite, sans commission.

## Affiliation

### Etat actuel

Le site affiche deja des produits affilies dans la grille du catalogue
`/products`.

Implementation actuelle :

- source de verite : `AFFILIATE_PRODUCTS` ;
- fichier principal : `src/app/lib/affiliate-products.ts` ;
- injection dans la grille : `ProductsGridInfinite` ;
- images locales : `public/affiliate/` ;
- source actuelle : Temu ;
- label visible : `Patrocinado`.

La documentation feature dediee est ici :

- `docs-site/content/features/produits-affilies.mdx`

### Role business

L'affiliation permet de monetiser une partie de l'audience sans demander de
paiement aux vendeuses et sans gerer la transaction entre acheteur et vendeur.

Avantages :

- revenu passif avec peu d'operations ;
- pas de paiement vendeur ;
- pas de gestion de litiges ou remboursements ;
- monetise aussi les visiteurs qui ne contactent aucune vendeuse ;
- peut rester coherente si les produits sont utiles au contexte mode/revente.

Produits affilies coherents :

- rasoir anti-peluches ;
- rangements pour vetements ;
- housses de protection ;
- cintres ;
- sacs de stockage ;
- accessoires pour photo produit ;
- emballage simple pour remise ou envoi.

### Limites

L'affiliation ne doit pas devenir le coeur du modele economique.

Risques :

- revenu probablement faible sans volume important ;
- dependance a un programme externe ;
- controle limite sur les prix, disponibilites et pages de destination ;
- confusion si les cartes ressemblent trop aux produits du marketplace ;
- perte de confiance si les cartes sponsorisees apparaissent trop tot ou trop
  souvent.

### Regles a maintenir

Les cartes affiliees doivent rester separees du vrai catalogue :

- label `Patrocinado` toujours visible ;
- pas de page detail produit ;
- pas de presence dans `/api/products` ;
- pas de presence dans le sitemap ;
- pas de presence dans les filtres Supabase ;
- pas de presence dans la newsletter catalogue ;
- ouverture vers le lien externe dans un nouvel onglet ;
- cadence d'affichage conservative.

L'objectif est de generer un revenu complementaire sans donner l'impression que
circular.moda vend directement ces produits.

### Mesure

Evenements a suivre :

- impression carte affiliee ;
- clic carte affiliee ;
- source du clic ;
- position dans la grille ;
- produit affilie clique.

Table possible :

```sql
affiliate_events
- id
- affiliate_product_id
- affiliate_source
- event_type
- page
- grid_index
- metadata
- created_at
```

Evenements possibles :

- `affiliate_impression`;
- `affiliate_click`.

## Boosts de visibilite

### Principe

Une vendeuse paie pour donner plus de visibilite a une prenda pendant une duree
limitee, par exemple 7 jours.

Offre de depart possible :

- `Destacar mi prenda 7 dias` ;
- affichage dans le bloc `Destacados` du catalogue ;
- badge visuel sur la carte produit ;
- presence possible dans une newsletter ;
- lien de partage prepare pour WhatsApp ou Instagram.

### Pourquoi c'est prioritaire

Le boost est l'offre payante la plus simple a comprendre et a tester.

Elle monetise une douleur directe : vendre plus vite. Elle ne demande pas de
controler la transaction finale, puisque la vente peut continuer a se faire via
WhatsApp.

Elle s'appuie sur des briques deja presentes :

- `products.featured` existe deja dans Supabase ;
- `/products` affiche deja un bloc `Destacados` ;
- les cartes produit savent deja afficher un etat `featured` ;
- la newsletter catalogue peut devenir une surface de visibilite.

### Point de vigilance

Ne pas promettre que le produit sera toujours tout en haut du catalogue
principal.

Risques :

- experience acheteur degradee si des produits faibles passent devant les bons
  produits ;
- impression de catalogue trop publicitaire ;
- pagination plus complexe si le tri principal change.

Formulations recommandees :

- `Mas visibilidad durante 7 dias` ;
- `Aparece en Destacados` ;
- `Puede aparecer en la newsletter` ;
- `Sin comisiones sobre la venta`.

Formulations a eviter :

- `Siempre arriba del catalogo` ;
- `Venta garantizada` ;
- `Mas mensajes asegurados`.

### Schema de donnees recommande

Ne pas utiliser uniquement `products.featured` comme mecanisme payant final.
Ce champ sert aujourd'hui plutot a la curation editoriale.

Table dediee recommandee :

```sql
product_promotions
- id
- product_id
- user_id
- type
- status
- starts_at
- ends_at
- source
- created_at
- updated_at
```

Valeurs possibles :

- `type`: `catalogue_boost`, `newsletter_boost`, `home_feature`;
- `status`: `pending_payment`, `active`, `expired`, `cancelled`;
- `source`: `manual`, `paid`, `subscription_quota`, `admin`.

### Impact catalogue

Court terme :

- garder le tri principal du catalogue par `created_at` ;
- utiliser les boosts seulement dans le bloc `Destacados` ;
- eviter de modifier la pagination principale.

Moyen terme :

- introduire un ranking explicite ;
- mixer produits recents, qualite visuelle et promotions actives ;
- revoir le curseur de pagination pour tenir compte de `promotion_score`,
  `created_at` et `id`.

### Impact front-end

Sur `/me` :

- bouton `Destacar` sur chaque produit ;
- etat de promotion actif/inactif ;
- date de fin du boost ;
- CTA apres publication : `Queres vender mas rapido?`.

Dans le catalogue :

- badge clair ;
- distinction possible entre `Destacado` editorial et `Impulsado` payant ;
- nombre de produits boostes plafonne.

Dans l'admin :

- voir les promotions actives ;
- activer ou desactiver une promotion ;
- verifier les paiements manuels au debut.

## Compte Plus ou Pro

### Principe

Un abonnement vendeur donne acces a des avantages recurrents.

Fonctionnalites possibles :

- boosts mensuels inclus ;
- analyse IA pour remplir les fiches produit ;
- vitrine vendeur amelioree ;
- statistiques basiques ;
- badge vendeur actif ou verifie ;
- publication prioritaire ;
- tri manuel des produits dans la vitrine.

### Avis

Le compte Plus/Pro est interessant, mais plutot en deuxieme phase.

Avec peu d'audience, une vendeuse aura du mal a justifier un abonnement mensuel
si la valeur percue depend surtout du nombre d'acheteurs actifs. Le boost
ponctuel est plus facile a tester.

Le compte Pro devient pertinent quand il combine :

- visibilite ;
- gain de temps ;
- credibilite ;
- donnees de performance.

Il ne doit pas seulement signifier que les vetements sont plus hauts dans le
catalogue.

### Schema de donnees recommande

```sql
seller_subscriptions
- id
- user_id
- plan
- status
- current_period_start
- current_period_end
- provider
- provider_customer_id
- provider_subscription_id
- created_at
- updated_at
```

```sql
seller_entitlements
- id
- user_id
- period_start
- period_end
- boost_credits_total
- boost_credits_used
- ai_credits_total
- ai_credits_used
- created_at
- updated_at
```

Ne pas surcharger `users` avec toute la logique business. Les abonnements,
quotas et paiements doivent rester dans des tables dediees.

### Badge premium

Le helper actuel `isPremiumSeller(productCount)` donne un statut visuel base sur
le nombre de produits. Quand les plans payants arriveront, il faudra separer :

- prestige gagne par activite ;
- statut payant ;
- badge vendeur verifie ;
- droits fonctionnels reels.

Regle future possible :

```ts
isPremiumSeller(productCount) || sellerPlan === 'plus'
```

Cette regle devra rester explicite pour ne pas confondre qualite, anciennete et
paiement.

## IA payante

### Principe

L'IA analyse les photos et une description courte, puis propose :

- nom du produit ;
- categorie ;
- couleur ;
- taille ;
- genre ;
- prix si mentionne ;
- description courte optimisee.

### Etat actuel

Une route existe deja cote admin :

```http
POST /api/admin/ai-analyze-product
```

Elle utilise OpenAI et les options Supabase existantes. Elle n'est pas encore
une fonctionnalite vendeur publique.

### Avis

C'est une bonne fonctionnalite Plus/Pro, car elle fait gagner du temps a la
vendeuse et ne depend pas uniquement de l'audience.

Options de packaging :

- quelques analyses gratuites pour tester ;
- analyses supplementaires payantes ;
- analyses incluses dans le plan Plus/Pro.

### Garde-fous

Avant exposition vendeur :

- verifier l'authentification ;
- limiter le nombre d'images ;
- limiter la taille des fichiers ;
- ajouter un quota par utilisateur ;
- logger les appels ;
- ne jamais laisser l'IA controler `featured` ou une promotion ;
- forcer une validation utilisateur avant publication.

Table utile :

```sql
ai_usage_events
- id
- user_id
- product_id
- action
- input_image_count
- status
- cost_estimate
- created_at
```

## Commissions

### Commission sur achat

Cette option est deconseillee a court terme.

Raisons :

- le site ne controle pas la transaction finale ;
- la conversation et la vente se font via WhatsApp ;
- il est difficile de savoir si une vente a vraiment eu lieu ;
- il faut gerer paiements, remboursements, litiges, fraude et support ;
- cela contredit potentiellement la promesse `sin comisiones`.

Pour rendre ce modele fiable, il faudrait internaliser le paiement acheteur et
ajouter une logique marketplace beaucoup plus lourde.

### Commission sur publication

Faire payer chaque publication est plus simple techniquement, mais risque de
freiner l'offre de produits. Pour une marketplace jeune, il est plus important
d'augmenter l'inventaire que de le taxer.

Cette option peut etre testee plus tard si la demande vendeur est forte.

## Paiement

### Court terme

Le paiement ne doit pas bloquer le test business.

Approche recommandee :

- paiement manuel par lien ;
- verification manuelle cote admin ;
- activation manuelle du boost ;
- mesure des resultats.

Cela permet de tester le prix psychologique, la comprehension de l'offre et le
taux de conversion du CTA.

### Fournisseurs

Pour l'Argentine, Mercado Pago semble etre le fournisseur naturel a etudier en
premier.

Documentation officielle consultee le 2026-08-27 :

- Mercado Pago Developers : https://www.mercadopago.com.ar/developers/es/docs
- Stripe Global Availability : https://stripe.com/global

Constat a cette date :

- Mercado Pago propose une documentation locale Argentine et des solutions de
  checkout ;
- Stripe publie une liste officielle de disponibilite par pays, a verifier
  avant toute integration si l'Argentine devient supportee.

Decision :

- commencer par des liens Mercado Pago ou une validation manuelle ;
- ne pas integrer un paiement complet avant preuve de demande ;
- garder les tables pretes pour connecter un provider plus tard.

produite.

Evenements a suivre :

- vue fiche produit ;
- clic WhatsApp depuis fiche produit ;
- clic WhatsApp depuis vitrine vendeur ;
- clic `Destacar` ;
- impression produit booste ;
- clic produit booste ;
- impression carte affiliee ;
- clic carte affiliee ;
- conversion apres CTA de boost.

## Roadmap

### Phase 0 : preparation technique

- Ajouter `product_promotions`, `seller_entitlements` et `product_events`.
- Garder `products.featured` pour la curation existante.
- Ajouter une couche de lecture pour les promotions actives.
- Ajouter une mesure minimale des clics WhatsApp et affilies.

### Phase 1 : test manuel du boost

- Ajouter un CTA `Destacar` dans `/me`.
- Rediriger vers WhatsApp ou un lien Mercado Pago manuel.
- Activer le boost en admin apres validation.
- Afficher le produit dans `Destacados`.
- Mesurer vues et clics.

### Phase 2 : boost automatise

- Creer une page ou modal de checkout.
- Ajouter `pending_payment` puis activation par webhook.
- Envoyer confirmation vendeur.
- Afficher l'historique des boosts dans `/me`.

### Phase 3 : compte Plus/Pro

- Ajouter des quotas mensuels de boosts et d'IA.
- Ajouter une vitrine vendeur enrichie.
- Ajouter des stats simples.
- Introduire un badge payant distinct du badge de vendeur actif.

### Phase 4 : marketplace transactionnelle

- Etudier seulement si le volume le justifie.
- Ajouter paiement acheteur, commandes, remboursements et litiges.
- Reconsiderer eventuellement une commission.

## Decisions provisoires

- Garder l'affiliation comme revenu complementaire discret, clairement signale
  et limite a des produits utiles au contexte mode/revente.
- Ne pas lancer de commission sur vente maintenant.
- Ne pas faire payer la publication standard maintenant.
- Tester d'abord un boost vendeur simple.
- Preparer techniquement un futur compte Plus/Pro, sans le lancer tout de
  suite.
- Exposer l'IA aux vendeurs seulement avec quotas, limites et logs.
- Commencer avec paiement manuel ou lien Mercado Pago avant une integration
  complete.
