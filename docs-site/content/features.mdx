# Features du site

Cette page documente les features importantes de `circular.moda`.

Chaque feature garde la meme structure :

- une **version simple**, pour comprendre rapidement ce que fait la feature ;
- une **version detaillee**, avec des blocs repliables pour ne pas surcharger la
  page et le sommaire Nextra.

## Newsletter catalogue automatique

### Version simple

La newsletter catalogue permet a une personne de laisser son email pour recevoir
les nouvelles pieces du catalogue une fois par mois.

Quand l'utilisateur s'inscrit depuis le site, l'email est ajoute dans Brevo et
dans Supabase. Brevo sert a stocker le contact cote marketing et a envoyer les
emails. Supabase sert a garder l'etat de l'abonnement : email actif, date
d'inscription, prochaine date d'envoi, dernier envoi et eventuelle erreur.

Le systeme fonctionne avec un cycle mensuel. Le `cron` Vercel passe tous les
jours, mais il n'envoie pas un email tous les jours a chaque personne. Il verifie
simplement quels abonnes ont une date `next_send_at` arrivee. Si une personne
s'est inscrite aujourd'hui, son premier email catalogue est planifie environ un
mois plus tard, puis le cycle continue mois par mois.

Chaque email contient un lien de desinscription. Quand l'utilisateur clique sur
ce lien, son abonnement est marque comme `unsubscribed` dans Supabase et le
contact est aussi retire de la liste Brevo de la newsletter catalogue.

### Version detaillee

<details>
<summary><strong>Services utilises</strong></summary>

- **Next.js** expose les routes API, le formulaire, la page de desinscription et
  le rendu HTML de l'email.
- **Supabase** garde les abonnements newsletter et l'historique des cycles
  d'envoi.
- **Brevo** garde le contact dans une liste et envoie les emails transactionnels.
- **Vercel Cron** appelle la route d'envoi automatiquement selon le planning de
  production.

</details>

<details>
<summary><strong>Parcours d'inscription</strong></summary>

1. L'utilisateur ouvre la carte newsletter du catalogue et entre son email.
2. Le client appelle `POST /api/catalogue-subscribe`.
3. La route normalise et valide l'email.
4. L'email est ajoute ou mis a jour dans la liste Brevo catalogue.
5. Une ligne est creee ou mise a jour dans `catalogue_subscriptions`.
6. `next_send_at` est calcule pour le meme jour du mois suivant, a l'heure
   d'envoi configuree.

Si l'email etait deja actif, le planning existant est conserve. Si l'ajout Brevo
reussit mais que l'ecriture Supabase echoue, la route tente de retirer le contact
de la liste Brevo pour eviter un etat incoherent.

</details>

<details>
<summary><strong>Cycle mensuel d'envoi</strong></summary>

Le planning Vercel appelle `GET /api/cron/send-catalogue` tous les jours a
`13:00 UTC`. Cette execution quotidienne sert seulement a trouver les
abonnements dus.

La route cron :

1. verifie le header `Authorization: Bearer ${CRON_SECRET}` ;
2. remet en `active` les lignes restees trop longtemps en `processing` ;
3. selectionne les lignes `catalogue_subscriptions` avec `status = active` et
   `next_send_at <= now` ;
4. claim chaque ligne en la passant en `processing` ;
5. cherche les produits ajoutes depuis la derniere fenetre d'envoi ;
6. utilise les dernieres pieces du catalogue en fallback s'il n'y a pas de
   nouveaux produits ;
7. rend le HTML de l'email dans le code ;
8. envoie l'email via Brevo transactional ;
9. enregistre le cycle dans `catalogue_delivery_cycles` ;
10. replace l'abonne en `active` avec un nouveau `next_send_at` un mois plus
    tard.

La limite d'envoi quotidienne est controlee par `BREVO_DAILY_SEND_CAP`, avec une
valeur par defaut de `250`.

</details>

<details>
<summary><strong>Desinscription et synchronisation Brevo</strong></summary>

Chaque email contient un lien signe vers `/newsletter/unsubscribe`. Le token
contient l'email normalise et une signature HMAC basee sur
`NEWSLETTER_TOKEN_SECRET`.

Quand l'utilisateur se desinscrit depuis ce lien :

- `catalogue_subscriptions.status` passe a `unsubscribed` ;
- `processing_started_at` est remis a `null` ;
- le contact est retire de la liste Brevo catalogue.

Brevo peut aussi notifier l'application via le webhook transactionnel. Les
evenements `delivered`, `unsubscribed`, `blocked`, `hard_bounce`, `spam`,
`error` et `invalid` mettent a jour `catalogue_delivery_cycles` et, quand
l'email est disponible, `catalogue_subscriptions`.

</details>

<details>
<summary><strong>Tables Supabase</strong></summary>

La feature utilise deux tables principales :

- `catalogue_subscriptions` : une ligne par email inscrit, avec le statut, la
  date d'inscription, la prochaine date d'envoi et les informations d'erreur.
- `catalogue_delivery_cycles` : une ligne par cycle d'envoi, avec la fenetre de
  produits, le type d'envoi, le nombre de produits, l'id de message Brevo et le
  statut de livraison.

Le schema SQL de reference est dans
[`docs/sql/catalogue-newsletter.sql`](../../docs/sql/catalogue-newsletter.sql).

</details>

## Login passwordless avec Supabase

### Version simple

Le login du site fonctionne sans mot de passe. L'utilisateur donne son email,
Supabase lui envoie un lien de connexion, puis l'utilisateur clique sur ce lien
pour ouvrir une session.

Il y a deux parcours proches :

- **login** : pour une personne qui a deja un compte ;
- **signup** : pour creer un compte avec un email.

Apres le clic dans l'email, Supabase confirme que le lien est valide et le site
cree une session dans le navigateur. Si c'est une nouvelle inscription, le
contact est aussi ajoute dans Brevo. Ensuite, si le profil n'est pas complet,
l'utilisateur passe par la page `welcome` pour ajouter son nom et son WhatsApp.

La table Supabase Auth garde l'identite de connexion. La table applicative
`users` garde les informations utiles au site : nom, telephone WhatsApp et lien
vers l'utilisateur Supabase Auth. Brevo sert a garder les utilisateurs dans une
liste marketing/contact, avec l'email au signup puis le nom et le telephone
quand le profil est complete.

### Version detaillee

<details>
<summary><strong>Services utilises</strong></summary>

- **Supabase Auth** gere le passwordless login, les magic links, les sessions et
  les cookies.
- **Supabase Postgres** stocke le profil applicatif dans `public.users`.
- **Next.js** expose les pages login/signup, la route de confirmation et les API
  de profil.
- **Vercel** heberge les routes et fournit les variables d'environnement qui
  construisent les URLs de confirmation.
- **Brevo** recoit les contacts utilisateurs via API. Pour l'email de login
  lui-meme, le code passe par Supabase Auth ; si Brevo SMTP est utilise, cette
  configuration vit dans le dashboard Supabase/Auth et non dans ce repo.

</details>

<details>
<summary><strong>Etat Supabase constate</strong></summary>

Lecture read-only effectuee le `2026-08-22`, sans afficher de donnees
personnelles :

- `auth.users` : 149 utilisateurs Auth.
- `public.users` : 161 profils applicatifs.
- Colonnes detectees sur `public.users` : `id`, `created_at`, `name`, `phone`,
  `user_id`.
- Profils avec `user_id` lie a Auth : 93.
- Profils sans lien Auth detecte : 68.
- Supabase Auth expose `external.email = true` et `disable_signup = false`.
- `mailer_autoconfirm = false`, donc l'email doit etre confirme par lien.
- Les providers sociaux sont desactives dans les settings Auth visibles.

Les profils sans `user_id` sont probablement des donnees historiques ou des
profils crees avant le flux Auth actuel. Ils ne doivent pas etre supprimes sans
audit, car des produits peuvent encore referencer `users.id` via `products.owner`.

</details>

<details>
<summary><strong>Parcours login</strong></summary>

1. L'utilisateur arrive sur `/login`.
2. La page verifie cote client si une session Supabase existe deja.
3. Si une session existe, l'utilisateur est redirige vers `next` ou `/me`.
4. Sinon, `LoginForm` appelle `supabase.auth.signInWithOtp`.
5. En mode `login`, `shouldCreateUser` vaut `false`.
6. Supabase envoie le magic link a l'email saisi.
7. L'URL de confirmation pointe vers `/auth/confirm`.
8. Quand l'utilisateur clique, `/auth/confirm` echange le `code` ou verifie le
   `token_hash`.
9. Supabase pose les cookies de session via `@supabase/ssr`.
10. Le site redirige vers `next` si ce chemin commence par `/`, sinon vers `/me`.

Si le lien est expire ou invalide, `/auth/confirm` redirige vers `/login` avec
`error=access_denied`. Le formulaire transforme cette erreur en message lisible.

</details>

<details>
<summary><strong>Parcours signup</strong></summary>

1. L'utilisateur arrive sur `/signup`.
2. Le meme composant `LoginForm` est utilise avec `mode="signup"`.
3. En mode signup, `shouldCreateUser` vaut `true`.
4. Le magic link contient `intent=signup`.
5. Apres confirmation, `/auth/confirm` recupere l'utilisateur courant.
6. Si l'utilisateur a un email, le contact est upsert dans Brevo via
   `upsertBrevoUserContact`.
7. Le contact Brevo est ajoute a `BREVO_USERS_LIST_ID`.
8. Si le profil applicatif n'est pas complet, `/me` redirige vers `/welcome`.
9. `/welcome` demande `name` et `phone`.
10. `PUT /api/me` cree ou met a jour la ligne `public.users`.
11. Apres sauvegarde du profil, `PUT /api/me` resynchronise Brevo avec
    `FIRSTNAME` et `SMS`.

La table `public.users` ne stocke pas l'email. L'email affiche dans le profil
vient de Supabase Auth, tandis que `public.users.user_id` relie le profil au
compte Auth.

</details>

<details>
<summary><strong>Protection des pages et routes</strong></summary>

Le middleware Next.js protege actuellement :

- `/me/:path*`
- `/welcome`

Quand aucun claim Supabase n'est present, le middleware redirige vers `/login`.
Quand un utilisateur connecte essaie d'aller sur `/login` ou `/auth`, le
middleware redirige vers `/me`.

Les routes API sensibles verifient aussi l'utilisateur avec le client serveur
Supabase :

- `GET /api/me` lit le profil et les produits du vendeur connecte.
- `PUT /api/me` cree ou met a jour le profil du vendeur connecte.
- `POST /api/me/upload-product` refuse la publication si l'utilisateur n'est
  pas connecte ou n'a pas encore de profil.
- Les routes produit sous `/api/me/products/[id]` relient les actions au
  vendeur connecte.

Les liens UI utilisent `signupUrl(nextPath)` et `loginUrl(nextPath)` pour garder
un parametre `next`. Exemple : le bouton `Vender ahora` envoie vers
`/signup?next=/me/product/add`.

</details>

<details>
<summary><strong>Brevo et contacts utilisateurs</strong></summary>

La sync Brevo des utilisateurs ne sert pas a authentifier la session. Elle sert
a garder une liste de contacts coherente avec les comptes du site.

Le helper `upsertBrevoUserContact` :

- normalise l'email ;
- ajoute le contact dans `BREVO_USERS_LIST_ID` ;
- utilise `updateEnabled: true` pour mettre a jour un contact existant ;
- ajoute `FIRSTNAME` si le nom est connu ;
- ajoute `SMS` si le telephone peut etre normalise en format argentin `+54...`.

Il y a deux moments de sync :

- apres confirmation signup, avec email seulement si le profil n'est pas encore
  complete ;
- apres `PUT /api/me`, avec nom et telephone.

Le script `scripts/import-supabase-users-to-brevo.mjs` sert de backfill manuel.
Il lit tous les users Supabase Auth, joint les profils `public.users` via
`user_id`, puis prepare des upserts Brevo. Son mode `--dry-run` imprime les
emails ; ne pas copier sa sortie dans la documentation ou dans un ticket public.

</details>

<details>
<summary><strong>Vercel et URLs de callback</strong></summary>

Vercel n'a pas de route speciale pour le login dans `vercel.json`. Son role est
principalement de fournir l'environnement d'execution et les variables.

Le callback envoye a Supabase est construit dans le navigateur :

```text
${NEXT_PUBLIC_SITE_URL || window.location.origin}/auth/confirm?next=...&intent=...
```

Points importants :

- `NEXT_PUBLIC_SITE_URL` doit pointer vers le domaine attendu en production si
  on veut des liens stables.
- Si `NEXT_PUBLIC_SITE_URL` est absent, le site utilise `window.location.origin`,
  ce qui est pratique en local ou preview.
- Les URLs de callback doivent etre autorisees dans le dashboard Supabase Auth.
- Si une preview Vercel doit tester le login, son domaine doit etre accepte par
  Supabase Auth ou le lien peut etre refuse.

</details>

<details>
<summary><strong>Variables d'environnement</strong></summary>

Variables utilisees par le flux login/signup :

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- `BREVO_API_KEY`
- `BREVO_USERS_LIST_ID`
- `NEXT_PUBLIC_SITE_URL`

Notes :

- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` est utilise par les clients
  `@supabase/ssr` navigateur et serveur.
- `SUPABASE_SERVICE_ROLE_KEY` est utilise par les scripts et certains helpers
  serveur historiques ; ne jamais l'exposer cote client.
- `BREVO_API_KEY` et `BREVO_USERS_LIST_ID` sont necessaires pour la sync contact
  utilisateur.
- Les credentials SMTP Brevo de Supabase Auth ne sont pas presents dans le repo.
  Ils doivent etre verifies dans Supabase Dashboard > Auth > Emails/SMTP.

</details>

## Espace vendeur

### Version simple

L'espace vendeur permet a une personne connectee de gerer son profil et ses
prendas depuis le site.

Le parcours commence apres le login. Si le profil n'est pas encore complet, le
site demande un nom et un numero WhatsApp. Une fois ce profil cree, le vendeur
peut publier une nouvelle prenda, modifier une prenda existante, supprimer une
prenda et partager sa vitrine publique.

Supabase Auth gere la session. La table `users` garde le profil vendeur. La
table `products` garde les prendas, avec un lien vers le vendeur via `owner`.
Les images sont envoyees dans Supabase Storage, puis les URLs publiques sont
stockees sur le produit.

Quand le vendeur met a jour son profil, le contact Brevo utilisateur est aussi
mis a jour avec le nom et le telephone. Cette sync ne sert pas au login, elle
sert au suivi marketing/contact.

### Version detaillee

<details>
<summary><strong>Services utilises</strong></summary>

- **Supabase Auth** garde l'utilisateur connecte et les cookies de session.
- **Supabase Postgres** stocke les profils vendeurs dans `users` et les prendas
  dans `products`.
- **Supabase Storage** stocke les images uploades dans le bucket `storage`.
- **Next.js** expose les pages vendeur, les routes API et le middleware de
  protection.
- **Brevo** recoit la mise a jour contact utilisateur apres sauvegarde du
  profil.

</details>

<details>
<summary><strong>Parcours profil vendeur</strong></summary>

Apres connexion, l'utilisateur arrive generalement sur `/me`.

La page `/me` :

1. verifie la session Supabase cote client ;
2. appelle `GET /api/me` ;
3. recupere le profil `users` lie a `auth.users.id` via `users.user_id` ;
4. recupere les produits du vendeur via `products.owner = users.id` ;
5. redirige vers `/welcome` si `name` ou `phone` manque.

La page `/welcome` utilise le meme formulaire de profil que `/me`. Elle force la
creation du profil avant de laisser l'utilisateur publier une prenda.

La sauvegarde profil passe par `PUT /api/me` :

1. l'API recupere l'utilisateur Auth courant ;
2. elle normalise le telephone argentin en format `+54...` ;
3. elle cree ou met a jour la ligne `users` ;
4. elle synchronise Brevo avec `email`, `FIRSTNAME` et `SMS` quand c'est
   possible.

</details>

<details>
<summary><strong>Publication d'une prenda</strong></summary>

Le vendeur publie depuis `/me/product/add`.

La page charge les options produit avec les APIs :

- `GET /api/categories`
- `GET /api/colors`
- `GET /api/genders`

Ces options viennent des tables Supabase `categories`, `colors` et `genders`.
Elles servent a limiter les valeurs envoyees dans `products`.

Au submit, la page appelle `POST /api/me/upload-product`.

La route :

1. verifie que l'utilisateur est connecte ;
2. verifie qu'un profil `users` existe ;
3. lit les champs `name`, `price`, `size`, `color`, `category`, `gender`,
   `description` et `images` ;
4. valide les fichiers image avec `getUploadedImageMetadata` ;
5. genere un `public_id` UUID ;
6. upload chaque image dans Supabase Storage sous `products/{public_id}-N.ext` ;
7. insere le produit dans `products` avec `owner = users.id` ;
8. declenche une revalidation produit pour rafraichir le catalogue.

Le champ `featured` est force a `false` dans le parcours vendeur.

</details>

<details>
<summary><strong>Edition et suppression d'une prenda</strong></summary>

Le vendeur edite depuis `/me/product/[id]/edit`.

La page appelle d'abord `GET /api/me/products/[id]`. L'API ne renvoie le produit
que si :

- l'utilisateur est connecte ;
- le profil `users` existe ;
- le produit appartient a ce vendeur via `products.owner`.

La mise a jour passe par `PUT /api/me/products/[id]`. Le vendeur peut garder ou
retirer des images existantes et ajouter de nouvelles images. Les nouvelles
images sont uploadees dans Supabase Storage avec le `public_id` existant.

La suppression passe par `DELETE /api/me/products/[id]`. L'API supprime la ligne
`products` seulement si le produit appartient au vendeur connecte. Apres update
ou delete, le code revalide les pages catalogue et produit concernees.

Point a noter : la suppression retire la ligne produit, mais le code lu ne
supprime pas explicitement les fichiers deja presents dans Supabase Storage.

</details>

<details>
<summary><strong>Vitrine publique vendeur</strong></summary>

Chaque vendeur avec des produits peut avoir une page publique `/user/[id]`.

Cette page :

- lit le profil public avec `getPublicUserById` ;
- lit les produits via `getProductsByOwnerId` ;
- affiche le nom du vendeur, le nombre de prendas et les cartes produits ;
- permet de partager l'URL de la vitrine ;
- affiche un badge premium quand le vendeur atteint le seuil defini dans
  `seller-tier.ts`.

La page `/me` affiche aussi un bloc "Tu vitrina publica" pour copier ou ouvrir
le lien `/user/{id}`.

</details>

<details>
<summary><strong>Protection et ownership</strong></summary>

Le middleware protege :

- `/me/:path*`
- `/welcome`

Les routes API de l'espace vendeur refont quand meme une verification serveur
avec Supabase. C'est important car la protection UI ne suffit pas pour securiser
une mutation.

Les endpoints de produit vendeur filtrent toujours avec :

- l'utilisateur Auth courant ;
- le profil `users` lie a cet Auth user ;
- `products.owner = users.id`.

Cette logique evite qu'un vendeur modifie ou supprime une prenda qui appartient
a un autre vendeur.

</details>

Stockage :

- bucket Supabase Storage : `storage`
- prefix images produit : `products/`

## Catalogue produits

### Version simple

Le catalogue produits est la partie du site qui affiche les prendas disponibles.
La page principale est `/products`.

Les produits viennent de Supabase. Le catalogue affiche d'abord une premiere
page de produits, puis charge la suite automatiquement quand l'utilisateur
descend dans la page. L'utilisateur peut rechercher et filtrer par categorie,
couleur, genre, taille et prix.

Le catalogue contient aussi des produits mis en avant, des cartes sponsorisees
affiliees et des cartes newsletter pour convertir les visiteurs en abonnes.

Chaque produit a sa page detail `/products/[slug]`. Cette page affiche les
images, les informations produit, le vendeur, le bouton WhatsApp, les autres
prendas du meme vendeur et des produits suggeres.

Le catalogue utilise ISR et le cache Next.js. En pratique, les pages sont
rafraichies automatiquement toutes les 5 minutes au maximum, et les mutations de
produits declenchent aussi une revalidation ciblee pour que les changements
arrivent plus vite.

### Version detaillee

<details>
<summary><strong>Services utilises</strong></summary>

- **Supabase Postgres** est la source principale pour `products`, `users`,
  `categories`, `colors` et `genders`.
- **Supabase Storage** sert les images produit.
- **Next.js App Router** rend `/products`, `/products/[slug]`, les APIs filtre
  et l'ISR.
- **Next.js data cache** garde les lectures produit avec des tags de cache.
- **Vercel** execute les pages en production et applique le comportement ISR.
- **Brevo** est indirectement implique via les cartes newsletter du catalogue.

</details>

<details>
<summary><strong>Chargement du catalogue</strong></summary>

La page `/products` est rendue cote serveur.

Elle charge :

1. les options de filtres avec `getProductFilterOptions` ;
2. les filtres actifs depuis les query params ;
3. la premiere page de produits avec `getProductsPage` ;
4. les produits mis en avant avec `getFeaturedProductsList` ;
5. les cartes UI via `transformProductsToCards`.

La suite du catalogue est chargee cote client par `ProductsGridInfinite`.
Quand le sentinel de bas de page devient visible, le composant appelle
`GET /api/products` avec `limit`, `cursor` et les filtres actifs.

La pagination est basee sur un curseur `{ created_at, id }`, encode en base64.
Ce choix evite les problemes classiques de pagination par offset quand de
nouveaux produits sont ajoutes.

</details>

<details>
<summary><strong>Recherche et filtres</strong></summary>

Filtres supportes :

- `q`
- `category`
- `color`
- `gender`
- `size`
- `priceMin`
- `priceMax`

Les filtres sont ecrits dans l'URL avec `URLSearchParams`. Cela rend la page
partageable et permet au serveur de reconstruire l'etat au chargement.

Les options de filtres viennent de Supabase :

- `GET /api/categories`
- `GET /api/colors`
- `GET /api/genders`

Les valeurs envoyees par l'URL sont normalisees puis resolues contre les options
existantes. Si une valeur ne correspond pas a une option connue, elle est
ignoree plutot que de lancer une requete incoherente.

La recherche `q` cherche dans `name`, `sku` et `description` cote Supabase.

</details>

<details>
<summary><strong>ISR, cache et revalidation</strong></summary>

La partie catalogue a deux niveaux de cache a comprendre.

Premier niveau : les routes page.

- `/products` declare `export const revalidate = 300`.
- `/products/[slug]` declare aussi `export const revalidate = 300`.
- `/products/[slug]` garde `dynamicParams = true`, donc un nouveau slug peut
  etre genere a la premiere requete meme s'il n'etait pas connu au build.

Deuxieme niveau : les lectures data.

Les helpers dans `src/app/lib/products.ts` utilisent `unstable_cache` avec :

- `PRODUCTS_ISR_SECONDS = 300`
- tag global `products`
- tag detail `product:{slug}` pour une page produit precise

Cela signifie qu'une lecture produit peut etre servie depuis le cache pendant
environ 5 minutes, sauf si une revalidation ciblee invalide le tag avant.

Les mutations produit appelees par le site declenchent directement
`revalidateProductContent` :

- creation admin ;
- creation vendeur ;
- edition vendeur ;
- suppression vendeur.

Cette fonction appelle `revalidateTag` et `revalidatePath` sur :

- `/products`
- `/products/{slug}`
- tag `products`
- tag `product:{slug}`

Il existe aussi `POST /api/revalidate`, protege par `REVALIDATE_SECRET`, pour
permettre a une source externe comme Supabase trigger ou Edge Function de
forcer la revalidation apres une modification faite hors application.

Point important : `GET /api/products` renvoie une reponse HTTP `no-store` pour
l'infinite scroll, mais les donnees lues par cette route passent quand meme par
les helpers de cache Next.js.

</details>

<details>
<summary><strong>Page detail produit</strong></summary>

La page `/products/[slug]` cherche le produit via `getProductBySlug`.

Le lookup Supabase essaie d'abord de recuperer le `public_id` depuis le slug au
format `{nom-produit}-{uuid}`. Si ce format ne marche pas, il essaie la colonne
`slug`.

La page produit :

- genere des metadata dynamiques ;
- choisit une image Open Graph/Twitter ;
- recupere le vendeur lie au produit ;
- affiche les images via `ProductImageGallery` ;
- affiche les infos via `ProductInfo` ;
- construit un lien WhatsApp ;
- affiche les autres produits du meme vendeur ;
- affiche des produits suggeres.

Le vendeur est optionnel : si la recuperation vendeur echoue, la page produit
continue de rendre les informations produit.

</details>

<details>
<summary><strong>Images produit</strong></summary>

Les produits Supabase stockent leurs images comme URLs publiques dans
`products.images`.

Pour l'affichage catalogue et detail, le site passe par `/api/image`.
Cette route :

1. accepte uniquement les URLs publiques Supabase Storage du projet ;
2. fetch l'image source ;
3. applique un resize optionnel avec `sharp` ;
4. corrige certains cas d'orientation EXIF ;
5. convertit en WebP quand le processing reussit ;
6. cache le resultat.

Les cartes catalogue utilisent une largeur reduite pour limiter l'egress. La
page detail utilise une hauteur maximum plus grande et des thumbnails separes.

Le script `normalize-product-image-orientation.mjs` sert de backfill ponctuel
pour corriger les fichiers deja stockes quand il faut que les URLs brutes soient
correctes partout, y compris dans les previews sociales.

</details>

<details>
<summary><strong>Produits mis en avant</strong></summary>

Les produits avec `featured = true` sont affiches en haut du catalogue dans le
bloc `Destacados`.

La selection vient de Supabase via `getFeaturedProductsList`. Elle est aussi
cachee avec le tag global `products`, donc une modification de featured doit
revalider le catalogue.

Les scripts d'exploitation permettent :

- de generer des contact sheets pour selection visuelle ;
- de preview/apply un batch de SKUs featured ;
- de vider les anciens featured avant d'appliquer le nouveau batch.

</details>

<details>
<summary><strong>Cartes newsletter et cartes affiliees</strong></summary>

La grille catalogue peut injecter deux types de cartes qui ne sont pas des
produits Supabase classiques.

Cartes newsletter :

- `CatalogueNewsletterCard` apparait a intervalle regulier dans la grille ;
- elle appelle `POST /api/catalogue-subscribe` ;
- elle alimente la feature newsletter catalogue automatique.

Cartes affiliees :

- les donnees sont statiques dans `affiliate-products.ts` ;
- elles apparaissent seulement cote client dans la grille `/products` ;
- elles sont marquees `Patrocinado` ;
- elles ne sont pas renvoyees par `/api/products` ;
- elles ne doivent pas apparaitre dans le sitemap, les pages detail ou la
  newsletter catalogue.

</details>

## Back-office admin et analyse IA produit

### Version simple

Le back-office admin permet d'ajouter des produits au catalogue sans passer par
le parcours vendeur connecte.

L'admin peut choisir un vendeur existant ou creer un nouveau vendeur, ajouter
des photos, remplir les champs produit et envoyer le tout vers Supabase. Il
existe aussi un mode d'analyse IA : l'admin donne une description et des images,
puis OpenAI propose automatiquement un nom, un prix, une taille, une couleur,
une categorie, un genre et une description courte.

Cette feature est pratique pour importer ou corriger rapidement des produits.
Elle touche plusieurs parties sensibles : OpenAI, Supabase Postgres, Supabase
Storage, les tables de lookup et la revalidation du catalogue.

### Version detaillee

<details>
<summary><strong>Services utilises</strong></summary>

- **Next.js** expose la page admin et les routes API.
- **OpenAI** analyse les images produit et la description texte.
- **Supabase Postgres** stocke les utilisateurs, les produits et les valeurs de
  reference.
- **Supabase Storage** stocke les images produit dans le bucket `storage`.
- **Next.js cache / ISR** est invalide apres creation produit.

</details>

<details>
<summary><strong>Parcours admin</strong></summary>

La page `/admin/upload-product` charge au demarrage :

- les couleurs via `/api/colors` ;
- les categories via `/api/categories` ;
- les genres via `/api/genders` ;
- les utilisateurs via `/api/admin/users`.

L'admin peut ensuite :

1. ajouter des images ;
2. choisir un utilisateur existant ou en creer un ;
3. remplir manuellement les champs produit ;
4. activer ou utiliser l'analyse IA ;
5. envoyer le formulaire vers `POST /api/admin/upload-product`.

La route d'upload valide le produit, genere un `public_id`, upload les images
vers Supabase Storage, insere la ligne dans `products`, puis declenche la
revalidation du catalogue.

</details>

<details>
<summary><strong>Analyse IA</strong></summary>

Le mode IA appelle `POST /api/admin/ai-analyze-product`.

La route :

1. recupere les valeurs valides dans `categories`, `colors` et `genders` ;
2. convertit les images en base64 ;
3. envoie les images et le texte a OpenAI ;
4. demande une reponse JSON stricte en espagnol argentin ;
5. nettoie les champs retournes ;
6. renvoie les donnees au formulaire.

Ensuite, le hook client remappe les valeurs IA contre les valeurs autorisees
dans Supabase. Si l'IA propose une couleur ou une categorie inconnue, le champ
est vide et un warning demande une selection manuelle.

</details>

<details>
<summary><strong>Creation ou selection de vendeur</strong></summary>

Le composant `UserSelector` permet deux modes :

- selectionner un vendeur existant depuis la table `users` ;
- creer un nouveau vendeur avec `name` et `phone`.

La route `POST /api/admin/users` verifie d'abord si un utilisateur avec le meme
telephone existe deja. Si oui, elle renvoie cet utilisateur au lieu d'en creer
un nouveau. Sinon, elle cree une ligne dans `users`.

Ces profils admin peuvent ne pas etre lies a Supabase Auth via `user_id`. C'est
normal pour certains vendeurs historiques ou crees manuellement, mais il faut le
prendre en compte avant de refactorer la relation `users` / `auth.users`.

</details>

<details>
<summary><strong>Protection et limites</strong></summary>

Le code lu expose `/admin/upload-product` et les routes `/api/admin/*`. La
documentation ne montre pas de garde d'auth admin dediee sur ces endpoints.

Avant d'ouvrir ou de renforcer cette zone, verifier :

- si la protection est faite ailleurs dans l'infrastructure ;
- si la route doit etre limitee par middleware ;
- si un role admin doit etre ajoute dans Supabase ;
- si les endpoints admin doivent refuser les appels anonymes cote serveur.

Ce point est important car l'API admin peut creer des users, uploader des images
et inserer des produits.

</details>

## Blog MDX et contenu editorial

### Version simple

Le blog permet de publier des articles depuis des fichiers MDX dans le depot.
Chaque fichier devient un article public avec son slug, sa page detail, son
image, son extrait, son auteur et ses metadata SEO.

La page `/blog` liste les articles publies. Chaque article est disponible sur
`/blog/[slug]`. Les articles peuvent afficher un hero, le contenu principal et
des articles lies.

Le blog est statique : les pages sont generees au build a partir des fichiers
dans `content/blog`.

### Version detaillee

<details>
<summary><strong>Source de contenu</strong></summary>

Les articles vivent dans `content/blog/*.mdx`.

Le nom du fichier devient le slug. Exemple :

```text

```

Le frontmatter controle les informations principales :

- `title`
- `excerpt`
- `author`
- `publishedAt`
- `updatedAt`
- `featuredImage`
- `readTime`
- `published`

Seuls les articles avec `published: true` sont retournes par
`getAllBlogArticles`.

</details>

<details>
<summary><strong>Rendu des pages</strong></summary>

ancien et affiche l'article principal en carte mise en avant.

1. genere les slugs statiques avec `generateStaticParams` ;
2. charge l'article par slug ;
3. genere les metadata avec `generateBlogMetadata` ;
4. rend `BlogHero`, `BlogContent` et `RelatedArticles`.

`revalidate = false` indique que les articles sont pleinement statiques. Pour
mettre un article a jour en production, il faut reconstruire/deployer le site.

</details>

<details>
<summary><strong>Articles lies, tags et recherche</strong></summary>

Le code contient des helpers pour :

- recuperer les articles recents ;
- chercher dans les titres, extraits et contenus ;
- recuperer des articles lies ;
- formater la date ;
- calculer le temps de lecture.

Le composant `BlogTags` existe pour une interface de tags, mais les articles
charges actuellement initialisent `tags` avec un tableau vide dans `blog.ts`.
Si on veut activer un vrai filtrage par tags, il faut lire les tags du
frontmatter et verifier les composants `BlogFilter` / `BlogTags`.

</details>

<details>
<summary><strong>SEO blog</strong></summary>

Le blog genere :

- metadata globales sur `/blog` ;
- metadata dynamiques pour chaque article ;
- Open Graph type `article` ;

## Pipeline images et media produit

### Version simple

Les images produit sont au centre du catalogue. Elles peuvent etre uploadees par
un vendeur ou par l'admin, stockees dans Supabase Storage, puis servies via un
proxy image interne pour reduire le poids et limiter l'egress Supabase.

Le site gere aussi les images manquantes, les fallbacks, les thumbnails, le zoom
sur la page detail et un script de correction d'orientation pour les anciennes
photos.

### Version detaillee

<details>
<summary><strong>Upload et validation</strong></summary>

Les routes d'upload vendeur et admin utilisent `getUploadedImageMetadata` pour
verifier qu'un fichier ressemble bien a une image et pour determiner son
extension/content-type.

Les images sont stockees dans Supabase Storage :

```text
bucket: storage
prefix: products/
```

Pour un nouveau produit, le nom de fichier utilise le `public_id` UUID du
produit. Pour une edition vendeur, les nouvelles images gardent le `public_id`
existant avec un suffixe horodate.

</details>

<details>
<summary><strong>Proxy image</strong></summary>

`/api/image` accepte une URL Supabase Storage publique via le parametre `url`.
La route refuse les URLs qui ne viennent pas du projet Supabase attendu.

Elle peut recevoir :

- `w` pour largeur max ;
- `h` pour hauteur max.

Elle utilise `sharp` pour resize, auto-orienter certains cas EXIF et convertir
en WebP. Le resultat est cache avec un cache memoire par instance et
`unstable_cache`.

</details>

<details>
<summary><strong>Affichage et fallback</strong></summary>

Les cartes produit utilisent une version reduite des images via
`CARD_IMAGE_WIDTH`.

La page detail utilise :

- `DETAIL_MAIN_MAX_HEIGHT` pour l'image principale ;
- `THUMB_SIZE` pour les thumbnails ;
- `ExternalImage` pour gerer les erreurs de chargement et fallback ;
- `ProductImageGallery` pour selectionner une image et afficher le zoom desktop.

Le code garde encore de la compatibilite avec d'anciens formats Airtable :
images objet, fichiers locaux et IDs commencant par `rec`.

</details>

<details>
<summary><strong>Backfill orientation</strong></summary>

Le proxy corrige l'affichage sur le site, mais certains services externes lisent
l'URL Supabase brute pour les previews sociales.

Le script `normalize-product-image-orientation.mjs` sert a corriger directement
les fichiers stockes. Il est prevu comme backfill ponctuel :

- mode `--dry-run` pour previsualiser ;
- mode `--limit=N` pour tester sur un petit lot ;
- execution complete pour traiter toutes les images.

Le script est idempotent et evite de tourner les images deja correctes avec un
tag EXIF stale.

</details>

## Operations metier et scripts

### Version simple

Le projet contient plusieurs scripts pour aider a exploiter le site sans tout
faire a la main dans Supabase : tester la connexion, recuperer un cache local de
produits, choisir les produits mis en avant, corriger les images et importer des
contacts utilisateurs dans Brevo.

Ces scripts ne sont pas des pages publiques, mais ils font partie du projet. Ils
doivent etre documentes parce qu'ils peuvent modifier la base ou preparer des
donnees utilisees en production.

### Version detaillee

<details>
<summary><strong>Featured products</strong></summary>

Le workflow featured products est operationnel :

1. recuperer ou verifier le cache produits ;
2. generer des contact sheets pour revue visuelle ;
3. choisir une liste de SKUs ;
4. lancer `featured:apply` sans `--apply` pour preview ;
5. relancer avec `--apply` pour ecrire dans Supabase.

Le script d'application vide d'abord les featured existants, puis marque les
SKUs fournis comme `featured = true`.

Les notes business historiques sont dans `docs/business/`.

</details>

<details>
<summary><strong>Imports Brevo et donnees sensibles</strong></summary>

`import-supabase-users-to-brevo.mjs` lit Supabase Auth avec pagination, joint les
profils `users`, normalise le telephone et upsert les contacts dans Brevo.

Toujours lancer d'abord :

```bash
node scripts/import-supabase-users-to-brevo.mjs --list-id=4 --dry-run
```

La sortie peut contenir des emails. Ne pas copier cette sortie dans la doc, dans
un ticket public ou dans un prompt partage.

</details>
