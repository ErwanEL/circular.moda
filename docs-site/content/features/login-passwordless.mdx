# Login passwordless avec Supabase

## Version simple

Le login du site fonctionne sans mot de passe. L'utilisateur donne son email,
Supabase lui envoie un lien de connexion, puis l'utilisateur clique sur ce lien
pour ouvrir une session.

Il y a deux parcours proches :

- **login** : pour une personne qui a deja un compte ;
- **signup** : pour creer un compte avec un email.

Apres le clic dans l'email, Supabase confirme que le lien est valide et le site
cree une session dans le navigateur. Si c'est une nouvelle inscription, le
contact est aussi ajoute dans Brevo. Ensuite, si le profil n'est pas complet,
l'utilisateur passe par la page `welcome` pour ajouter son nom et son WhatsApp.

La table Supabase Auth garde l'identite de connexion. La table applicative
`users` garde les informations utiles au site : nom, telephone WhatsApp et lien
vers l'utilisateur Supabase Auth. Brevo sert a garder les utilisateurs dans une
liste marketing/contact, avec l'email au signup puis le nom et le telephone
quand le profil est complete.

## Version detaillee

<details>
<summary><strong>Services utilises</strong></summary>

- **Supabase Auth** gere le passwordless login, les magic links, les sessions et
  les cookies.
- **Supabase Postgres** stocke le profil applicatif dans `public.users`.
- **Next.js** expose les pages login/signup, la route de confirmation et les API
  de profil.
- **Vercel** heberge les routes et fournit les variables d'environnement qui
  construisent les URLs de confirmation.
- **Brevo** recoit les contacts utilisateurs via API. Pour l'email de login
  lui-meme, le code passe par Supabase Auth ; si Brevo SMTP est utilise, cette
  configuration vit dans le dashboard Supabase/Auth et non dans ce repo.

</details>

<details>
<summary><strong>Etat Supabase constate</strong></summary>

Lecture read-only effectuee le `2026-08-22`, sans afficher de donnees
personnelles :

- `auth.users` : 149 utilisateurs Auth.
- `public.users` : 161 profils applicatifs.
- Colonnes detectees sur `public.users` : `id`, `created_at`, `name`, `phone`,
  `user_id`.
- Profils avec `user_id` lie a Auth : 93.
- Profils sans lien Auth detecte : 68.
- Supabase Auth expose `external.email = true` et `disable_signup = false`.
- `mailer_autoconfirm = false`, donc l'email doit etre confirme par lien.
- Les providers sociaux sont desactives dans les settings Auth visibles.

Les profils sans `user_id` sont probablement des donnees historiques ou des
profils crees avant le flux Auth actuel. Ils ne doivent pas etre supprimes sans
audit, car des produits peuvent encore referencer `users.id` via `products.owner`.

</details>

<details>
<summary><strong>Parcours login</strong></summary>

1. L'utilisateur arrive sur `/login`.
2. La page verifie cote client si une session Supabase existe deja.
3. Si une session existe, l'utilisateur est redirige vers `next` ou `/me`.
4. Sinon, `LoginForm` appelle `supabase.auth.signInWithOtp`.
5. En mode `login`, `shouldCreateUser` vaut `false`.
6. Supabase envoie le magic link a l'email saisi.
7. L'URL de confirmation pointe vers `/auth/confirm`.
8. Quand l'utilisateur clique, `/auth/confirm` echange le `code` ou verifie le
   `token_hash`.
9. Supabase pose les cookies de session via `@supabase/ssr`.
10. Le site redirige vers `next` si ce chemin commence par `/`, sinon vers `/me`.

Si le lien est expire ou invalide, `/auth/confirm` redirige vers `/login` avec
`error=access_denied`. Le formulaire transforme cette erreur en message lisible.

</details>

<details>
<summary><strong>Parcours signup</strong></summary>

1. L'utilisateur arrive sur `/signup`.
2. Le meme composant `LoginForm` est utilise avec `mode="signup"`.
3. En mode signup, `shouldCreateUser` vaut `true`.
4. Le magic link contient `intent=signup`.
5. Apres confirmation, `/auth/confirm` recupere l'utilisateur courant.
6. Si l'utilisateur a un email, le contact est upsert dans Brevo via
   `upsertBrevoUserContact`.
7. Le contact Brevo est ajoute a `BREVO_USERS_LIST_ID`.
8. Si le profil applicatif n'est pas complet, `/me` redirige vers `/welcome`.
9. `/welcome` demande `name` et `phone`.
10. `PUT /api/me` cree ou met a jour la ligne `public.users`.
11. Apres sauvegarde du profil, `PUT /api/me` resynchronise Brevo avec
    `FIRSTNAME` et `SMS`.

La table `public.users` ne stocke pas l'email. L'email affiche dans le profil
vient de Supabase Auth, tandis que `public.users.user_id` relie le profil au
compte Auth.

</details>

<details>
<summary><strong>Protection des pages et routes</strong></summary>

Le middleware Next.js protege actuellement :

- `/me/:path*`
- `/welcome`

Quand aucun claim Supabase n'est present, le middleware redirige vers `/login`.
Quand un utilisateur connecte essaie d'aller sur `/login` ou `/auth`, le
middleware redirige vers `/me`.

Les routes API sensibles verifient aussi l'utilisateur avec le client serveur
Supabase :

- `GET /api/me` lit le profil et les produits du vendeur connecte.
- `PUT /api/me` cree ou met a jour le profil du vendeur connecte.
- `POST /api/me/upload-product` refuse la publication si l'utilisateur n'est
  pas connecte ou n'a pas encore de profil.
- Les routes produit sous `/api/me/products/[id]` relient les actions au
  vendeur connecte.

Les liens UI utilisent `signupUrl(nextPath)` et `loginUrl(nextPath)` pour garder
un parametre `next`. Exemple : le bouton `Vender ahora` envoie vers
`/signup?next=/me/product/add`.

</details>

<details>
<summary><strong>Brevo et contacts utilisateurs</strong></summary>

La sync Brevo des utilisateurs ne sert pas a authentifier la session. Elle sert
a garder une liste de contacts coherente avec les comptes du site.

Le helper `upsertBrevoUserContact` :

- normalise l'email ;
- ajoute le contact dans `BREVO_USERS_LIST_ID` ;
- utilise `updateEnabled: true` pour mettre a jour un contact existant ;
- ajoute `FIRSTNAME` si le nom est connu ;
- ajoute `SMS` si le telephone peut etre normalise en format argentin `+54...`.

Il y a deux moments de sync :

- apres confirmation signup, avec email seulement si le profil n'est pas encore
  complete ;
- apres `PUT /api/me`, avec nom et telephone.

Le script `scripts/import-supabase-users-to-brevo.mjs` sert de backfill manuel.
Il lit tous les users Supabase Auth, joint les profils `public.users` via
`user_id`, puis prepare des upserts Brevo. Son mode `--dry-run` imprime les
emails ; ne pas copier sa sortie dans la documentation ou dans un ticket public.

</details>

<details>
<summary><strong>Vercel et URLs de callback</strong></summary>

Vercel n'a pas de route speciale pour le login dans `vercel.json`. Son role est
principalement de fournir l'environnement d'execution et les variables.

Le callback envoye a Supabase est construit dans le navigateur :

```text
${NEXT_PUBLIC_SITE_URL || window.location.origin}/auth/confirm?next=...&intent=...
```

Points importants :

- `NEXT_PUBLIC_SITE_URL` doit pointer vers le domaine attendu en production si
  on veut des liens stables.
- Si `NEXT_PUBLIC_SITE_URL` est absent, le site utilise `window.location.origin`,
  ce qui est pratique en local ou preview.
- Les URLs de callback doivent etre autorisees dans le dashboard Supabase Auth.
- Si une preview Vercel doit tester le login, son domaine doit etre accepte par
  Supabase Auth ou le lien peut etre refuse.

</details>

<details>
<summary><strong>Variables d'environnement</strong></summary>

Variables utilisees par le flux login/signup :

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- `BREVO_API_KEY`
- `BREVO_USERS_LIST_ID`
- `NEXT_PUBLIC_SITE_URL`

Notes :

- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` est utilise par les clients
  `@supabase/ssr` navigateur et serveur.
- `SUPABASE_SERVICE_ROLE_KEY` est utilise par les scripts et certains helpers
  serveur historiques ; ne jamais l'exposer cote client.
- `BREVO_API_KEY` et `BREVO_USERS_LIST_ID` sont necessaires pour la sync contact
  utilisateur.
- Les credentials SMTP Brevo de Supabase Auth ne sont pas presents dans le repo.
  Ils doivent etre verifies dans Supabase Dashboard > Auth > Emails/SMTP.

</details>

<details>
<summary><strong>Tests et verifications</strong></summary>

Tests manuels a faire apres changement :

1. Aller sur `/signup?next=/me/product/add`.
2. Entrer un nouvel email de test.
3. Cliquer le magic link.
4. Verifier la redirection vers `/welcome` si le profil est incomplet.
5. Completer nom et WhatsApp.
6. Verifier la redirection vers `/me`.
7. Verifier que le bouton `Publicar prenda` est accessible.
8. Verifier dans Brevo que le contact a bien `FIRSTNAME` et `SMS`.
9. Se deconnecter depuis `/me`.
10. Tester `/login` avec le meme email.

Verifications techniques :

- `npm run docs:build` pour la documentation.
- `npm run build` pour verifier les routes Next.js.
- Dans Supabase Auth, confirmer que `email` est active et que les callback URLs
  incluent les domaines local/preview/production necessaires.
- Dans Vercel, confirmer les variables `NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_SITE_URL`,
  `BREVO_API_KEY` et `BREVO_USERS_LIST_ID`.

</details>
