# Vitrine vendeur publique

## Version simple

Chaque vendeur possède une adresse `/@pseudo`, modifiable depuis **Mi Perfil**.
Les anciennes adresses `/user/42` et les anciens pseudos redirigent vers
l'adresse actuelle. Les articles restent liés au même identifiant interne.

Les comptes existants reçoivent un pseudo `prenom-id` (par exemple `maria-42`).
Les accents sont retirés ; un prénom inutilisable devient `vendedor-id`.
Les pseudos sont uniques, insensibles à la casse, de 3 à 30 caractères,
composés de lettres ASCII, chiffres et tirets (sans tiret aux extrémités).
Certains noms comme `admin` et `support` sont réservés.

Le vendeur peut ajouter un identifiant Instagram ou un lien de profil. La
vitrine affiche un lien Instagram public ; cela ne vérifie pas la propriété du
compte et n'utilise ni OAuth ni l'API Instagram. Un bouton propose un pseudo
Circular à partir d'Instagram, mais le vendeur doit le sélectionner et sauvegarder.
Changer Instagram ne change jamais automatiquement l'adresse Circular.

## Version détaillée

### Migration et ordre de mise en service

**Appliquer [seller-usernames.sql](../../../docs/sql/seller-usernames.sql) dans
Supabase avant de mettre cette version du site en service.** La migration est
transactionnelle et réexécutable. Elle ajoute :

- `users.username` et `users.instagram_username` ;
- `seller_usernames`, registre des pseudos actuels et historiques ;
- des index uniques sur le pseudo et sur les comptes Auth liés, et deux triggers de validation/réservation ;
- les pseudos initiaux pour tous les comptes existants.

Les anciennes versions du site peuvent toujours créer un profil sans pseudo :
le trigger en génère un. Aucune modification des identifiants, articles ou
relations de propriétaire n'est nécessaire. En cas de retour à l'ancien code,
conserver les colonnes et le registre : les supprimer perdrait les réservations.

### Disponibilité, concurrence et sécurité

`GET /api/me/username?username=...` demande une session et indique uniquement la
disponibilité pour ce vendeur. Le formulaire temporise les requêtes et annule
les résultats devenus obsolètes. Une réponse « disponible » n'est pas une
réservation : la contrainte SQL décide lors de l'enregistrement.

`PUT /api/me` vérifie l'identité Supabase, valide les champs et met à jour le
profil du compte connecté. La réservation du pseudo fait partie de la même
transaction que la mise à jour grâce au trigger. Un conflit renvoie HTTP 409,
sans enregistrer partiellement les autres changements du profil.

Le registre n'est pas accessible directement aux rôles `anon`/`authenticated`.
Seul le serveur utilise la clé de service pour résoudre une adresse ou vérifier
sa disponibilité. Les fonctions des triggers ont un `search_path` vide, ne sont
pas appelables directement par les clients et vérifient aussi l'ownership du
profil pour les écritures des rôles clients.

Les anciens pseudos restent réservés. Le propriétaire peut les reprendre ; un
autre vendeur ne le peut pas. Après suppression du compte, la réservation reste
présente sans propriétaire, pour éviter la réattribution des anciens liens.

### Routes, référencement et cache

- `src/app/[handle]/page.tsx` accepte uniquement les segments commençant par `@`.
- `src/app/user/[id]/page.tsx` redirige en HTTP 308 vers le pseudo courant.
- Les anciens pseudos et les variantes de casse redirigent en 307 : leur cible
  peut changer. Cela évite les boucles de cache si un vendeur reprend son ancien pseudo.
- Un nom inconnu ou une réservation sans propriétaire renvoie 404.
- Les métadonnées canonical/Open Graph, le sitemap, le partage et les liens
  vendeurs utilisent la nouvelle adresse.
- La résolution des vitrines est dynamique pour éviter un pseudo obsolète
  après modification ; les produits conservent leur cache existant.
- Le composant partagé `ui/seller-storefront.tsx` conserve les cartes, le prénom,
  le badge premium et le partage, et ajoute le lien Instagram.

### Tests

```bash
npm test
npm run test:profile-db
npx tsc --noEmit --incremental false
npm run build
```

Les tests SQL utilisent une base PostgreSQL PGlite isolée en mémoire et ne
contactent jamais Supabase. Ils couvrent le backfill, les homonymes, les accents,
la réexécution, les alias, les conflits atomiques, les noms invalides et les
permissions, y compris avec une politique users volontairement permissive.

Après application sur Supabase, vérifier aussi avec deux comptes de test :

1. `/user/ID` redirige vers `/@prenom-id` et affiche les mêmes produits.
2. Modifier le pseudo dans `/me`, puis ouvrir l'ancien et le nouveau lien.
3. Demander le même pseudo depuis l'autre compte : refus sans perte des données.
4. Ajouter, modifier et retirer Instagram ; vérifier le lien public et la suggestion.
5. Vérifier le formulaire sur mobile, au clavier et avec un réseau lent.

### État de l'activation

La migration a été appliquée sur Supabase après renouvellement du jeton local.
Les 213 profils existants ont chacun un pseudo et une réservation correspondante.
Les 969 articles sont conservés ; l'empreinte des anciens champs de profil
(id, nom, téléphone, compte Auth) est identique avant et après migration.
Le registre est protégé par RLS et inaccessible directement aux rôles clients.
Le build de production passe avec le nouveau schéma. Les contrôles HTTP locaux
sur ce build confirment la redirection 308 depuis `/user/ID`, une vitrine en 200
avec canonical, la redirection 307 des majuscules, le 404 des pseudos inconnus,
le refus 401 des API profil sans session et les URLs personnalisées du sitemap.
Le paramètre de route accepte `@` et sa forme encodée `%40` ; un test couvre ce cas.
Les 41 tests applicatifs et les tests SQL isolés passent.

La mise en service sur Vercel nécessite le déploiement de ce code ; aucune
variable `SUPABASE_ACCESS_TOKEN` n'est nécessaire sur Vercel. Le parcours de
modification connecté reste à vérifier avec le compte de test de l'utilisateur.

## Boutique personnelle : en-tête et sélection

Depuis `/me`, le bloc **Mi boutique** permet de sauvegarder indépendamment :

- un nom de dressing facultatif (60 caractères), une présentation (300) et un quartier facultatif de CABA ;
- une photo JPG, PNG ou WebP de 3 Mo maximum, avec aperçu et suppression ;
- jusqu'à trois articles du vendeur, dans l'ordre de sélection.

Les champs vides restent facultatifs : prénom et initiales servent de repli.
La ville est fixée à Buenos Aires (CABA) ; le quartier choisi est affiché devant la ville. Les articles sélectionnés
apparaissent avant le catalogue et ne sont pas répétés dans celui-ci. Les IDs
supprimés ou transférés sont ignorés au rendu et lors de la prochaine sauvegarde.
Les collections restent une étape ultérieure.

Le bouton WhatsApp contacte **Circular**, avec l'URL de la boutique dans le
message, conformément au parcours de mise en relation existant. Aucun numéro
personnel du vendeur n'est ajouté aux données publiques.

### Stockage et validation

Appliquer `docs/sql/seller-storefront.sql` après la migration des pseudos, avant
de déployer ce code. Cette migration additive est réexécutable et conserve les
profils et produits. Elle ajoute `boutique_name`, `bio`, `city`, `avatar_url` et
`pinned_product_ids` à `users`. Un trigger interdit les doublons, les sélections
étrangères ou inexistantes ; une contrainte limite la sélection à trois articles.

`PUT /api/me/storefront` exige une session, recherche le profil lié au compte
Auth et sauvegarde avec le client RLS et un filtre propriétaire. Le serveur
vérifie aussi les articles sélectionnés. La photo est décodée, orientée, recadrée
au centre et convertie en WebP 512 × 512 sans métadonnées avant stockage dans
`storage/avatars/<auth-id>/<uuid>.webp`. Aucun URL d'image fourni par le formulaire
n'est accepté. Les uploads sont retirés si l'écriture du profil échoue.

La migration est appliquée sur Supabase : 215 profils et 972 articles conservés,
empreinte des identifiants, noms, téléphones, comptes Auth et pseudos inchangée.
Le code nécessite encore un déploiement Vercel.

### Vérification

```bash
npm test
node scripts/test-seller-storefront.cjs
npm run build
```

Validation réalisée : 43 tests applicatifs, tests SQL isolés, TypeScript, builds du site
et de la documentation. Le contrôle HTTP confirme la vitrine en 200, le canonical,
la redirection historique et le refus 401 des écritures sans session. L’en-tête
public a été vérifié dans Chrome sur ordinateur et à 390 px. Le formulaire
connecté et une sauvegarde réelle de photo restent à tester avec le compte utilisateur.

Les tests isolés couvrent les limites de texte, les IDs invalides, les articles
d'autres vendeurs, les doublons, l'ordre de sélection, l'absence de duplication
dans le catalogue et la suppression d'un article sélectionné.
Pour la recette connectée : enregistrer le dressing, ajouter/remplacer/retirer une
photo, sélectionner trois articles, vérifier que le quatrième est désactivé,
recharger `/me` et visiter la vitrine. Contrôler également le formulaire au clavier
et sur mobile. L'import automatique de photos WhatsApp/Instagram n'est pas prévu.

### Périmètre CABA

La migration `docs/sql/seller-caba-neighborhoods.sql`, à appliquer après
`seller-storefront.sql`, fixe `city` à `Buenos Aires (CABA)` et ajoute
`neighborhood`. Le quartier est facultatif et limité aux
[48 quartiers de CABA](https://buenosaires.gob.ar/gcaba_historico/mapas-tematicos-ba/mapas-de-barrios).
Le formulaire utilise une liste native accessible. Le serveur impose la ville
et valide le quartier ; les contraintes SQL protègent également les écritures directes.
Aucun quartier n'est inventé pour les profils existants. Une ancienne ville
correspondant exactement à un quartier est conservée dans le nouveau champ.
